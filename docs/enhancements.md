# Future enhancements

Things deliberately left out to stay within scope, with a clear path to add them:

| Enhancement                                            | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Enrichment indexing**                                | The `article_enrichments` table only indexes `status` today. Once sentiment/topic filters are exposed in the UI, add `btree(sentiment)` to back the sentiment aggregate/filter and `GIN(topics)` for tag filtering. Held back for now due to time constraints, and since the logic would be similar to what is already in place.                                                                                                                                                                                              |
| **Filtering & aggregating on enrichment**              | Extend the filter surface and the aggregate view to group/filter by `sentiment` and `topics`, not just date/source/language — turning enrichment from display-only into a queryable dimension.                                                                                                                                                                                                                                                                                                                                |
| **Relevance ranking (article vs. enrichment matches)** | Search currently treats the whole `search_vector` uniformly. A ranking system could weight matches by where they occur — a term in the original **headline/body** ranked above a term that only appears in **AI-generated** summary/topics — so human-authored content outranks model-derived text. Postgres supports this natively via `setweight()` on `tsvector` (e.g. headline = `A`, body = `B`, enrichment = `C`/`D`) combined with `ts_rank`, letting us order results by weighted relevance instead of recency alone. |
| **Aggregate rollups at scale**                         | For unbounded full-corpus dashboards, precompute the month/week counts into a **materialized view or periodic rollup table** rather than scanning the index on every request (noted under Indexing choices).                                                                                                                                                                                                                                                                                                                  |
| **Real job queue**                                     | Enrichment is script-driven but queue-ready (status + attempts + error message per work item); the natural next step is a proper worker queue picking up `pending`/`failed` rows with backoff.                                                                                                                                                                                                                                                                                                                                |
| **Self-hosted LLM model**                              | Experiment with self-hosted models to see whether this limits costs and improves the quality of the summaries provided.                                                                                                                                                                                                                                                                                                                                                                                                       |
